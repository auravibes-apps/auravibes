Research date: **2026-10-13**. This compares representative first-party repositories and documentation, not every browser automation project. Release/package versions and dates are those visible during this review.

## AuraVibes baseline and gaps

The built-in Browser skill currently defines 13 tools in [the skill registry](../../apps/auravibes_app/lib/services/skills/app_skill_registry.dart) and dispatches them through [the browser session notifier](../../apps/auravibes_app/lib/features/browser/providers/browser_session_notifier.dart): list/open/close/select tabs; navigate, back, forward, reload; execute JavaScript; read text, Markdown, HTML, or TOON; query up to five CSS matches; click one visible element; fill one supported non-password text field.

This covers URL-based new tabs, navigation in an existing tab, basic text extraction, and simple CSS-targeted actions. The page reader bounds output, removes scripts/styles/iframes/SVG/canvas, and clears form values. The biggest gap is a reliable observe → act → wait → verify loop: no accessibility snapshot or semantic find, no condition-based wait, no screenshot, and no keyboard-driven input. Current click/fill handlers use page JavaScript (`element.click()`, programmatic value setters, and synthetic input/change events), which can miss behavior that requires real pointer or keyboard input.

| Priority | Add to AuraVibes | Why |
| --- | --- | --- |
| 1 | Accessibility snapshot with stable refs, plus role/name/text/label find | Playwright MCP/CLI and `agent-browser` use accessible structure to target the control the agent just saw; keep CSS as fallback. |
| 2 | `browser_wait_for` for text, selector, URL, and page-load state with bounded timeouts | Navigation load completion does not prove an SPA control or result is ready. |
| 3 | Keyboard press/type, select/check, hover, and scroll actions | Covers focus, shortcuts, menus, and form controls that synthetic `click`/`fill` miss. |
| 4 | Viewport, element, and full-page screenshots | Covers canvas/image-heavy pages and lets the agent verify visible outcomes. |
| 5 | Dialog, popup/new-window, frame, upload, and download handling | Completes common browser workflows, but needs clear file/path permissions and user-consent rules. |
| 6 | Opt-in console and network summaries | Helps diagnose failed pages; bound output and redact credentials, cookies, and response data. |

Do not copy authenticated-profile, cookies, local-storage, stealth, or cloud-browser features into the conversation WebView by default. BrowserMCP and `mcp-chrome` operate a user’s existing Chrome profile; AuraVibes owns a WebView scoped to the conversation. The current skill also says not to read credentials or browser storage, while its general JavaScript tool can execute arbitrary page code. Treat that as a policy boundary to preserve or harden before adding more powerful actions. ([BrowserMCP architecture](https://github.com/BrowserMCP/mcp#readme), [`mcp-chrome` surface](https://github.com/hangwin/mcp-chrome/blob/master/docs/TOOLS.md))

## Product features versus ecosystem gaps

**Product features vary by intended layer.** Playwright and Chrome DevTools emphasize inspectable, stepwise control; Chrome DevTools adds browser diagnostics. Playwright CLI and `agent-browser` package that control as agent-oriented commands/skills. Browser Use and Stagehand add higher-level task/action abstractions. BrowserMCP and `mcp-chrome` prioritize the existing logged-in local browser; `mcp-chrome` documents broader browser data tools. These are different product choices, not a single feature ladder. ([Playwright comparison](https://github.com/microsoft/playwright-mcp#playwright-mcp), [Chrome DevTools tools](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md), [Browser Use tools](https://github.com/browser-use/browser-use/blob/main/skills/open-source/references/integrations.md), [Stagehand agent](https://github.com/browserbase/stagehand/blob/main/packages/docs/v2/basics/agent.mdx), [BrowserMCP README](https://github.com/BrowserMCP/mcp#readme), [mcp-chrome tools](https://github.com/hangwin/mcp-chrome#readme))

**Portability remains an ecosystem-level gap.** MCP supplies a common connection protocol, but sampled tools expose different action and reference models: Playwright snapshot refs/selectors, Chrome DevTools UIDs, Browser Use indexes, and Stagehand natural-language actions. Browser session handling also differs: isolated contexts, persistent CLI daemons, existing local profiles, and cloud profiles. Agent skills, state handoff, and policy therefore need product-specific adaptation; the reviewed docs do not define a shared cross-project action or session contract. This is an inference from the documented APIs, not a claim that MCP cannot carry one. ([Playwright capabilities](https://playwright.dev/mcp/capabilities), [Chrome DevTools tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md), [Browser Use local tools](https://github.com/browser-use/browser-use/blob/main/skills/open-source/references/integrations.md), [Stagehand agent](https://github.com/browserbase/stagehand/blob/main/packages/docs/v2/basics/agent.mdx))

**Page-authored tools are emerging, not a universal baseline.** WebMCP lets websites expose structured tools backed by their own application logic. Playwright, Chrome DevTools, and `agent-browser` document discovery/invocation support. The WebMCP source is a Draft Community Group Report dated 2026-10-09, explicitly not a W3C Standard; its implementation-status page lists Chrome and Edge origin trials. ([WebMCP draft](https://webmachinelearning.github.io/webmcp/), [implementation status](https://github.com/webmachinelearning/webmcp/blob/main/implementation-status.md), [Playwright CLI](https://playwright.dev/docs/getting-started-cli), [Chrome DevTools tools](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md), [`agent-browser`](https://github.com/vercel-labs/agent-browser#webmcp-experimental))

**Session access is a security boundary.** A tool attached to an authenticated profile may inherit the user’s logged-in access; Chrome DevTools states that MCP clients can inspect, debug, and modify browser data. Product controls differ, and page-provided text/tool metadata must remain untrusted. Treat profile reuse, uploads, downloads, page scripts, and write actions as host-policy decisions rather than effects of MCP transport alone. ([Chrome DevTools disclosure](https://github.com/ChromeDevTools/chrome-devtools-mcp#disclaimers), [Playwright access controls](https://playwright.dev/mcp/configuration/options), [`agent-browser` trust guidance](https://github.com/vercel-labs/agent-browser#webmcp-experimental))

## Coverage limits

- Checked first-party repositories, official project docs, and GitHub/npm release metadata for these representative surfaces. This is not an exhaustive repository census.
- Verified documented capabilities, browser/session boundaries, and the release tags/dates linked above. Did not install the projects, test compatibility, or run task-success, latency, token-cost, or security benchmarks.
- Feature claims describe vendor documentation; security and reliability claims were not independently tested. GitHub `main` docs are rolling references, while release links preserve version evidence.
