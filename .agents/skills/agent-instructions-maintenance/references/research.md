# Research notes: maintaining AGENTS.md and skills

Checked 2026-09-26. This is a focused source review, not a systematic review. Vendor guidance states recommended practice; repository studies use different agents, tasks, and outcomes. Treat effect sizes as context-specific. Refresh fast-changing product guidance before making a material policy decision.

## Findings

### Official Codex guidance

[Codex customization and AGENTS.md guidance](https://learn.chatgpt.com/docs/customization/overview) recommends starting with only useful instructions, recording recurring mistakes and review feedback, putting rules in the closest applicable file, and using skills for detailed reusable workflows. It also describes scheduled checks that look for guidance gaps and suggest updates. This directly supports proactive maintenance, but is product guidance rather than a controlled outcome study.

### GitHub Copilot support and size guidance

[GitHub's Copilot cloud-agent docs](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions) support repository `AGENTS.md` files, with the nearest file taking precedence. The same page's one-time generation prompt says generated instructions should be no longer than two pages. That is a prompt constraint for generated `.github/copilot-instructions.md`, not a GitHub `AGENTS.md` file limit; the current docs reviewed here do not specify a hard per-file length cap. GitHub's separate 30,000-character maximum applies to a custom-agent prompt. Copilot CLI combines applicable instruction files but does not define general precedence among them, so avoid conflicting copies. [GitHub's agent-skills docs](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills) explicitly support project skills under `.agents/skills`; Copilot loads a skill when its prompt and description make it relevant. GitHub documents a finite, model-dependent context window for Copilot CLI, so loaded instructions still have a context cost without a documented AGENTS.md cap.

### Studies of repository instruction files

- [Lulla et al., *On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents* (submitted 2026-01-28; revised 2026-03-30)](https://arxiv.org/abs/2601.20404) compared runs on 124 PR tasks across 10 repositories. With repository `AGENTS.md` files, median runtime was 28.64% lower and output tokens 16.58% lower, with comparable task completion. The study measures efficiency, not a general correctness improvement.
- [Gloaguen et al., *Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?* (2026-02-12; v2 2026-06-23)](https://arxiv.org/abs/2602.11988) tested four agent/model combinations on Python tasks: 300 SWE-bench Lite tasks and 138 tasks from 12 repositories with developer-authored files. Generated context did not significantly improve success and raised cost 20–23%; developer-authored context had a small, statistically non-significant average success increase over no context (+2.4%, p=.21), but did outperform generated context (p=.038) while still adding steps/cost. Repository overviews did not speed discovery of relevant files. In an ablation with documentation removed, generated context improved performance by 2.7% on average and outperformed developer-written context; Claude Code was excluded from that ablation for cost reasons. This supports context as a replacement when useful docs are absent, not as duplicated overview. Treat the specific percentages as setup-dependent; each agent sampled one completion per task.
- [Shepard and Albrecht, *Probe-and-Refine Tuning of Repository Guidance for Coding Agents* (2026-06-18)](https://arxiv.org/abs/2606.20512) iteratively refined repository guidance using bug-fix probes. On SWE-bench Verified with Qwen3.5-35B-A3B, mean resolve rate was 33.0% after refinement, versus 28.3% with the static starting guidance and 25.5% without guidance. Most gain came from producing more evaluable patches/reaching the right files, not higher per-patch precision. A cross-model experiment degraded when the model could not produce sufficiently diagnostic output. This supports evaluation-guided refinement and warns against assuming rules transfer unchanged across agents.

### Growth and feedback-loop evidence

- [Chakrabarti, *Why Does CLAUDE.md Keep Growing? Catastrophic Remembering in Agentic Coding* (2026-08-11)](https://arxiv.org/abs/2608.11095) reports an observational analysis of 247,694 instruction lifetimes across 1,867 repositories: instruction files grew by 226% over their lifetimes, with a net 4.9 instructions added per commit. The paper also reports experiments where comments preserving the reason behind instructions reduced simulated prompt growth and improved instruction following. This motivates preserving brief rationale for non-obvious rules and making pruning part of the lifecycle; it does not establish a universal file-size limit.
- [Aggarwal and Ghalaty, *Self-Improving AI Coding Agents Through Accumulated Behavioral Rules* (2026-07-13)](https://arxiv.org/abs/2607.13091) describes a 35+ service deployment that translated accepted review feedback into versioned rules. It reports no recurrence across nine tracked error classes in 74 post-rule session exposures. The observation covered 11 sessions in one deployment and had no controlled comparison, so treat it as an early practitioner report, not proof of broad effectiveness.

### Current vendor and format guidance

- OpenAI's [*Rethinking skills and prompts for GPT-6 Astra* (2026-09-11)](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) is unusually direct about maintenance: revisit old scaffolding as models improve; keep skill descriptions short and specific; descriptions that are broad or skills that overlap can cause wrong skill selection; use progressive disclosure; avoid elaborate recipes when the model can handle ambiguity; and point to documents only for the task that needs them. It also warns that repository skills serve other contributors' models, so guidance that helps one model can overconstrain another. This is vendor guidance for a specific model generation, not a universal guarantee; retain it as a reason to reassess assumptions after model or host changes.
- Anthropic's [Agent Skills engineering guide (2025-10-16; open standard announced 2025-12-18)](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) supports progressive disclosure: short metadata selects a skill, its `SKILL.md` gives the workflow, and linked references/scripts load only when relevant. It advises starting from observed task gaps, iterating on actual skill trajectories, keeping mutually exclusive workflows separate, and using code for operations where deterministic execution is better than generated prose. It also recommends auditing skills from less-trusted sources, including bundled scripts, dependencies, and network behavior.
- The [AGENTS.md project](https://agents.md/) describes the file as standard Markdown with no required headings and recommends nested files for subprojects. It says the closest file takes precedence. GitHub's [Copilot agent-skills documentation](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills) confirms project skills can live under `.agents/skills` and use `SKILL.md` plus optional referenced resources. These are format/platform facts; support and precedence can differ by agent host, so verify the current host when portability matters.

### Configuration smells found in repositories

- Dos Santos et al., [*Configuration Smells in AGENTS.md Files*](https://arxiv.org/abs/2606.15828) (arXiv v5, 2026-07-30; listed for SCAM 2026), derive six smells from a grey-literature review and analyze 100 popular repositories. Their heuristics flagged lint leakage in 62 files, context bloat in 42, skill leakage in 35, blind references in 16, initialization fossilization in 24, and conflicts in 28; 91 files had at least one flagged smell. The paper defines useful review prompts: avoid restating reliable lint rules, moving rare workflows into always-loaded files, naming references without explaining their role, preserving unreviewed initialization output, and leaving incompatible rules in place.
- Treat that prevalence cautiously. The sample was selected from the 100 most-starred repositories containing root `AGENTS.md` or `CLAUDE.md`, and detection mixed line-count/commit heuristics with LLM judgments reviewed by one author. Conflict detection had only 57% precision. Their 200-line cutoff is a detection heuristic borrowed from Claude guidance, not a validated universal limit or a causal result. Use the smell catalog to inspect behavior and maintenance risk, not to enforce quotas.

### Mixed outcome evidence: correctness is not the only measure

- The research does not support “AGENTS.md always helps” or “AGENTS.md is useless.” Lulla et al. report efficiency gains on 124 PR tasks, with comparable completion. Gloaguen et al. find no significant general success-rate benefit; generated files increased cost by 20–23%, and developer-authored files had a small non-significant improvement over no context while outperforming generated files. Agents followed instructions, but broad repository overviews did not help. Khatri's [two-agent ablation (2026-07-28)](https://arxiv.org/abs/2607.27250) reports no measurable correctness effect across 17 tasks, three repositories, two agents, and 288 runs, with effects bounded to roughly 10–15 percentage points by equivalence tests. It also reports one narrow process-efficiency case where an explicit “full suite is slow” warning reduced repeated full-suite runs for one agent and repository; that was exploratory, not a general effect.
- Gloaguen et al.'s documentation-removal ablation is an important boundary condition: when Markdown/docs were removed, generated context improved success by 2.7% on average. Context is more promising when it supplies missing facts than when it repeats discoverable documentation.
- McMillan's [factorial study of four file-structure variables (submitted 2026-05-11)](https://arxiv.org/abs/2605.10039) ran 1,650 Claude Code sessions and found no detectable effect from file size, instruction position, file architecture, or contradictions on a deliberately simple target-annotation adherence task. This is a useful counterweight to assuming a structural smell always causes measurable harm. Its single-agent, two-TypeScript-repository, narrow proxy outcome does not establish that size/conflicts never affect real task quality or cost.
- These studies use different task sets, agents, and measures, and the later Khatri work is a small, independent preprint. The useful inference is conditional: project rules may change search, tool use, testing, or cost without changing correctness; narrow non-standard requirements are better candidates for persistent guidance than generic overviews; test claims against the actual agent, workflow, and metric that matter here.

### Skill design and evaluation

- Anthropic's [skills guide](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) recommends starting from representative observed gaps and reviewing actual trajectories. OpenAI's [*Testing Agent Skills Systematically with Evals* (2026-01-22)](https://developers.openai.com/blog/eval-skills) recommends defining a few must-pass outcome, process, style, and efficiency checks; checking explicit, implicit, contextual, and negative-trigger examples; then using deterministic trace/state checks before adding qualitative grading. It suggests 10–20 prompts for a skill evaluation as a practical starter, not a mandatory minimum for every repository skill. Grow a case set from real failures and keep evaluation effort proportional to impact and recurrence.
- Anthropic's [skill-creator update (2026-03-03)](https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills) distinguishes **capability uplift** skills (techniques the base model lacks or applies inconsistently) from **encoded workflow preferences** (a team's desired sequence or criteria). Compare capability skills with a no-skill baseline after model upgrades; retire them when the base model reliably passes the relevant checks. Preference skills are more durable, but retain them only while they still match the real process. This framing helps prevent a model upgrade from either preserving obsolete coaching or accidentally dropping actual team policy.
- A skill's metadata is part of routing behavior. Test whether it activates for the intended task and stays inactive for adjacent tasks; distinguish “skill did not trigger” from “triggered but workflow failed.” Compare before/after under the same host/model when feasible, and record task outcome and process/cost signals. For trivial wording changes, review frontmatter, links, and scope without inventing a new benchmark harness.
- Skills are executable packaging as well as documentation. Review scripts and external instructions for file changes, dependencies, network calls, and permissions. Do not adopt third-party skill content without auditing what it asks the agent to execute.

### Practitioner experience at scale

- Anthropic's [lessons from building hundreds of Claude Code skills (2026-06-03)](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills) reports internal usage measurement via hooks to identify popular or under-triggering skills. It says many successful skills began as a few lines and one gotcha, then grew as real edge cases appeared. This is useful practitioner evidence for starting small and observing skill activation; the post does not provide controlled outcome data.
- Anthropic's [Warp case study](https://claude.com/blog/how-warp-builds-self-improving-agents-on-claude) describes a separate “improver” skill that observes accumulated human review feedback and proposes small edits to a base skill, with changes flowing through normal PR review. This is a concrete autonomous-maintenance pattern with human-reviewed patches, but published outcome measurements are limited. It suggests separating the work skill from the instruction-improver and making updates reviewable, rather than letting each task freely rewrite its own rules.

## Practical conclusions

1. A feedback loop is reasonable; unfiltered self-rewriting is not supported by the evidence. Promote verified corrections and repeated patterns, not every transient failure.
2. Diagnose before editing: missing, stale, contradictory, ignored, mis-scoped, redundant, over-triggering, and too broad need different fixes.
3. Keep `AGENTS.md` for short, durable, project-specific rules. Use scoped files and triggered skills for narrow procedures; use executable tooling for deterministic checks; make each reference explain when it applies.
4. Revisit assumptions after meaningful model, host, or repository changes. Do not schedule broad rewrites or enforce a line count without observed evidence.
5. Evaluate material changes against relevant tasks and adjacent non-trigger tasks. Check useful outcomes and process cost; preserve mixed findings and limitations rather than adopting a universal claim.
6. Prune stale rules, duplicate lint policy, unused procedures, broken references, and unsafe or unnecessary script behavior.
